# 規格編寫詳細方法

## 1.規格的核心目的

### Clean Room Design 中的規格定位

規格是 Clean Room Design 的**唯一合法資訊來源**：

```
原始程式碼（禁止接觸）
        ↓ ×不可傳遞
規格文件（唯一通道）
        ↓ ✅ 合法傳遞
新語言實現
```

**核心原則**：規格描述「做什麼」，絕不描述「怎麼做」。

### 規格的三大功能

| 功能 | 說明 |
|------|------|
| **資訊載體** | 移植者唯一可參考的文件 |
| **法律屏障** | 避免版權侵權的關鍵證據 |
| **契約基礎** | 測試驗證的標準依據 |

---

## 2. 規格應該包含的內容

### 必要項目

|項目 | 內容說明 |範例 |
|------|----------|------|
| **功能描述** | 模組/函數的用途與行為概要 | 「將數字陣列從小到大排序」 |
| **輸入規範** | 輸入資料的類型、格式、限制 | 「接收整數陣列，長度 ≥ 0」 |
| **輸出規範** |輸出資料的類型、格式、預期值 | 「返回排序後的陣列」 |
| **邊界條件** | 特殊情況的處理方式 | 「空陣列返回空陣列」 |
| **行為預期** | 在某種條件下應發生的結果 | 「已排序陣列不改變」 |

### 可選項目

| 項目 | 內容說明 | 使用場景 |
|------|----------|----------|
| **效率要求** |時間/空間複雜度要求 | 效率敏感的模組 |
| **錯誤處理** | 錯誤情況的處理策略 | 需要錯誤回報的模組 |
| **依賴關係** | 此模組依賴的其他模組 | 大型系統的模組 |
| **使用範例** | 具體的輸入/輸出範例 |複雜行為的模組 |

---

## 3. 規格絕對不可包含的內容

### 禁止項目清單

| 項目 | 原因 |洩漏範例 |
|------|------|----------|
| **具體程式碼片段** | 直接複製實現 | `for (int i = 0; i < n; i++)` |
| **變數命名** |洩漏原作者思路 | 「變數 `n` 存陣列長度」 |
| **算法結構** | 洩漏實現邏輯 | 「用雙重迴圈遍歷」 |
| **語言特性** | 限制實現者選擇 | 「用 `[a,b]=[b,a]` 交換」 |
| **實現技巧** |洩漏原作者經驗 | 「用位運算加速」 |
| **註解翻譯** | 直接複製註解 | 「原註解：//排序函數」 |

### 禁止項目的法律意義

| 洩漏類型 | 法律風險 |
|----------|----------|
| 程式碼片段 | **直接侵權** |
|算法結構 | 可能被視為「衍生作品」 |
|變數命名 | 可能被視為「結構性複製」 |
| 實現技巧 |可能被視為「商業秘密洩漏」 |

## 4. 規格編寫的標準流程

### Phase 1: 功能理解

**目標**：理解原程式碼的功能，而非實現。

```
步驟：
1.閱讀原程式碼的使用者介面（API）
2. 理解輸入/輸出的資料流
3. 分析行為模式（但不分析實現邏輯）
4. 記錄功能概要（自然語言）
```

**關鍵技巧**：
-問「這個函數做什麼？」而非「這個函數怎麼做？」
- 關注「使用者角度」而非「開發者角度」

### Phase 2: 輸入/輸出分析

**目標**：明確定義資料的型態與格式。

```
步驟：
1. 列出所有輸入參數
2. 記錄每個參數的類型（不記錄實際變數名）
3. 列出所有輸出結果
4. 記錄輸出的類型與格式
```

**範例**：
```
輸入：
- 數字陣列（整數集合）
- 陣列長度可為零或正整數

輸出：
-排序後的陣列（整數集合）
- 長度與輸入相同
```

### Phase 3:邊界條件識別

**目標**：識別特殊情況的處理。

```
常見邊界條件：
1. 空輸入（空陣列、null、空字串）
2. 單元素輸入
3.極端值（最大值、最小值）
4. 已處理狀態（已排序陣列）
5.錯誤輸入（無效資料）
```

**範例**：
```
邊界條件：
- 空陣列 →返回空陣列
- 單元素陣列 →返回原陣列
- 已排序陣列 →返回原陣列
```

### Phase 4: 行為描述

**目標**：用自然語言描述行為，不描述實現。

```
正確描述方式：
「比較相鄰元素，若前者較大則交換位置，重複直到整體有序」

錯誤描述方式：
「用雙重迴圈，外層 i從 0到 n-1，內層 j從 0到 n-i-1」
```

**關鍵技巧**：
- 用「直到」「當」「如果」等自然語言
- 避免「迴圈」「變數」「索引」等程式碼語言

### Phase 5:規格文件化

**目標**：整理成標準格式的規格文件。

```
標準格式：
1. 功能名稱
2. 功能描述
3. 輸入規範
4. 輸出規範
5. 邊界條件
6.行為預期
7.使用範例（可選）
```

## 5. 如何避免洩漏實現細節

### 五大檢查技巧

####技巧 1：抽象層級檢查

**問題**：「這段描述是在說『做什麼』還是『怎麼做』？」

|描述 |判定 |
|------|------|
| 「排序陣列」 | ✅做什麼（抽象） |
| 「用泡沫排序算法」 | ⚠️ 怎麼做（具體） |
| 「用雙重迴圈比較」 | ❌怎麼做（程式碼） |

**修正方法**：
- 「用泡沫排序算法」→「排序陣列（時間複雜度O(n²)）」
- 「用雙重迴圈比較」→「反覆比較並交換元素」

#### 技巧 2：變數名檢查

**問題**：「描述中是否包含具體變數名？」

| 描述 | 判定 |
|------|------|
| 「陣列長度」 | ✅抽象概念 |
| 「變數 n 存陣列長度」 | ❌具體變數名 |

**修正方法**：
- 「變數 n」→「陣列長度」

#### 技巧 3：程式碼語言檢查

**問題**：「描述中是否使用程式碼專用語言？」

| 語言 |判定 |
|------|------|
| 「迴圈」「索引」「指標」 | ❌程式碼語言 |
| 「反覆」「位置」「參考」 | ✅自然語言 |

**修正方法**：
- 「迴圈」→「反覆」
- 「索引」→「位置」
- 「指標」→「參考」

#### 技巧 4：語言特性檢查

**問題**：「描述是否依賴特定語言特性？」

|描述 |判定 |
|------|------|
| 「交換兩元素」 | ✅跨語言通用 |
| 「用 `[a,b]=[b,a]` 交換」 | ❌ JavaScript特性 |
| 「用位運算 XOR 交換」 | ❌特定技巧 |

**修正方法**：
- 「用 `[a,b]=[b,a]`」→「交換兩元素位置」

#### 技巧 5：原程式碼對比檢查

**問題**：「描述是否與原程式碼結構相似？」

| 情況 |風險 |
|------|------|
| 描述結構與原程式碼結構相似 | ❌高風險 |
| 描述結構與原程式碼結構不同 | ✅低風險 |

**修正方法**：
-重新組織描述，使其結構與原程式碼不同

## 6.規格審查 Checklist

### 寫入前檢查

| 檢查項 |問題 |通過標準 |
|--------|------|----------|
| **程式碼片段** | 是否包含任何程式碼區塊？ | 無程式碼區塊 |
| **變數命名** | 是否包含具體變數名？ | 使用抽象概念 |
| **算法結構** | 是否描述實現邏輯？ | 只描述行為 |
| **語言特性** | 是否依賴特定語言？ | 跨語言通用 |
| **實現技巧** | 是否洩漏原作者技巧？ | 只描述功能 |
| **註解翻譯** | 是否直接翻譯原註解？ | 重寫描述 |

### 寫入後審查

| 檢查項 | 問題 | 通過標準 |
|--------|------|----------|
| **抽象層級** | 是否為「做什麼」層級？ |抽象描述 |
| **完整性** | 是否涵蓋所有必要項？ | 功能完整 |
| **一致性** | 各部分是否一致？ | 無矛盾 |
| **可實現性** | 是否可根據規格實現？ | 可實現 |
| **可測試性** | 是否可根據規格測試？ | 可測試 |

## 7.實際範例：日誌模組規格

### Level 2 模組範例

#### 功能名稱

日誌記錄模組

#### 功能描述

將程式執行過程中的重要事件記錄到儲存媒體，供後續查詢與分析。

####輸入規範

| 輸入 |類型 |限制 |
|------|------|------|
| 日誌訊息 | 字串 | 長度 ≥ 0，可為空 |
| 日誌等級 |枚舉 | DEBUG、INFO、WARN、ERROR |
|時間戳記 |日期時間 | 可自動生成或外部提供 |

####輸出規範

|輸出 |類型 |說明 |
|------|------|------|
| 日誌記錄 | 文件/資料庫 | 持久化儲存 |
| 執行結果 | 成功/失敗 | 可選回報 |

####邊界條件

|情況 |處理方式 |
|------|----------|
| 空日誌訊息 | 不記錄或記錄空行 |
| 日誌等級為 ERROR |確保記錄成功 |
|儲存媒體無法寫入 |回報錯誤或降級處理 |

#### 行為預期

1. 根據日誌等級決定是否記錄（等級過濾）
2. 格式化日誌訊息（時間戳記+等級+訊息）
3. 寫入儲存媒體
4. 可選：回報執行結果

#### 使用範例

```
輸入：
訊息："使用者登入成功"
等級：INFO
時間：2026-04-27 14:30:00

輸出（日誌文件內容）：
[2026-04-27 14:30:00] INFO:使用者登入成功
```

#### 效率要求（可選）

- 寫入延遲：< 100ms
- 支援緩衝區批次寫入

## 8. AI Agent 規格編寫指南

### AI Agent 的特殊注意事項

| 注意事項 | 說明 |
|----------|------|
| **上下文汙染風險** | AI 可能在規格中「記住」原程式碼結構 |
| **抽象能力限制** | AI 可能難以完全抽象化描述 |
| **審查必要性** | AI 產出的規格必須人工審查 |

### AI Agent規格編寫流程

```
步驟 1：AI 分析原程式碼功能
        ↓
步驟 2：AI 產出初步規格
        ↓
步驟 3：人工審查規格（使用 Checklist）
        ↓
步驟 4：修正洩漏部分
        ↓
步驟 5：AI與人工共同確認
        ↓
步驟 6：規格文件化
```

### AI Agent產出規格的審查重點

|審查重點 | 問題範例 |
|----------|----------|
| **隱性程式碼** | AI 可能用「自然語言寫程式碼」 |
| **結構相似** | AI 可能複製原程式碼的邏輯結構 |
| **變數暗示** | AI 可能暗示原程式碼的變數名 |

## 9. 總結

### 規格編寫的核心心法

```
1.只看功能，不看實現
2. 只說「做什麼」，不說「怎麼做」
3. 用自然語言，不用程式碼語言
4. 用抽象概念，不用具體變數
5. 審查再審查，確保不洩漏
```

### 規格品質的三個標準

|標準 | 問題 |
|------|------|
| **法律安全** | 「是否可作為 Clean Room證據？」 |
| **實現可行** |「是否可根據規格實現？」 |
| **測試可行** | 「是否可根據規格測試？」 |
