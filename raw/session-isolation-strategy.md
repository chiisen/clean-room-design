# AI Agent Session 隔离策略

## 1. 问题本质

### 传统 Clean Room 的物理隔离

```
规格编写者房间（可看原代码）
        ↓ 规格文档（纸质）
        ↓ 物理传递
移植开发者房间（不可看原代码）
```

物理隔离确保：移植开发者**无法接触**原始代码。

### AI Agent 的信息隔离挑战

```
AI Agent 的上下文记忆
├── Session 内记忆（对话历史）
├── 跨 Session 记忆（MemPalace）
└── 模型训练数据（隐性记忆）
```

问题：AI Agent 在 Session A 看了原代码，Session B 可能"记得"。

## 2. 三层隔离策略

### Layer 1: Session 隔离（显式上下文）

| 策略 | 操作 | 效果 |
|------|------|------|
| **新 Session** | 每个阶段开启新对话 | 清除对话历史 |
| **不携带文件** | Session B 不打开原代码文件 | 无法读取原代码 |
| **只看规格** | Session B 只读取 `/raw/specs/*.md` | 信息来源受限 |

```
Session A（规格提取）
─────────────────────
输入：原代码仓库
操作：提取功能，不复制代码
输出：/raw/specs/*.md
结束：关闭 Session，不记录代码细节到 MemPalace

Session B（新实现）
─────────────────────
输入：/raw/specs/*.md（只有规格）
操作：根据规格写新代码
输出：新语言实现
限制：不打开原代码文件
```

### Layer 2: MemPalace 记录策略（跨 Session 记忆）

**关键规则**：MemPalace 只记录**规格内容**，不记录**代码细节**。

| 可记录 | 不可记录 |
|--------|----------|
| 功能描述 | 具体代码片段 |
| 输入/输出格式 | 变量命名 |
| 边界条件 | 算法细节（如循环结构） |
| 模块名称 | 实现技巧 |

**MemPalace 记录示例（正确）**：
```
SESSION:2026-04-27|PROJ:CRD|SPEC:日志模块|FUNC:写入日志到文件|INPUT:msg(string),level(enum)|OUTPUT:void|BOUNDARY:空msg→skip|★★★
```

**错误示例（泄漏代码）**：
```
SESSION:2026-04-27|PROJ:CRD|CODE:if(msg==null)return;File.write(msg);|★★★
```

### Layer 3: 规格文档的自我审查

规格文档编写后，需检查是否泄漏实现细节：

| 检查项 | 问题示例 | 修正 |
|--------|----------|------|
| **算法结构** | "用双重循环遍历" | → "遍历直到有序" |
| **变量命名** | "变量 `n` 存数组长度" | → "获取数组长度" |
| **语言特性** | "用 `[a,b] = [b,a]` 交换" | → "交换两元素" |
| **代码片段** | 包含任何代码块 | → 删除，用自然语言描述 |

## 3. 实际操作流程

### Phase 1: 规格提取（Session A）

```
用户指令：
"我有一个 JS 项目，帮我提取功能规格到 /raw/specs/"

AI 行为：
1. 读取原代码仓库
2. 提取功能描述（自然语言）
3. 编写规格文档 → /raw/specs/*.md
4. 记录到 MemPalace（只记录功能，不记录代码）
5. 结束 Session，建议用户开启新 Session

AI 输出：
"规格已提取到 /raw/specs/。请开启新 Session 进行实现，
 并告诉我'根据 /raw/specs/ 实现 C# 版本'。"
```

### Phase 2: 新实现（Session B）

```
用户指令：
"根据 /raw/specs/ 实现 C# 版本"

AI 行为：
1. 读取 /raw/specs/*.md（只有规格）
2. 不打开原代码文件
3. 根据规格写 C# 实现
4. 编写测试用例（根据规格的输入/输出）

AI 限制：
- 即使 MemPalace 有记录，也不主动查询原代码细节
- 如果规格不完整，向用户提问而非回看原代码
```

### Phase 3: 测试验证（Session C）

```
用户指令：
"验证 C# 实现是否符合规格"

AI 行为：
1. 运行测试用例
2. 对比输入/输出行为
3. 报告差异（如有）
4. 不对比代码结构
```

## 4. MemPalace 配合 Clean Room 的配置

### Wing 架构调整

```
wing: wing_clean_room_design
├── room: specs/           ← 功能规格（Session A 输出）
├── room: implementations/ ← 新实现记录（Session B 输出）
├── room: test-results/    ← 测试验证（Session C 输出）
└── room: decisions/       ← 移植决策记录
```

### 记录规则（写入 AGENTS.md）

```markdown
## Clean Room 记录规则

1. **规格阶段**：只记录功能描述，不记录代码
2. **实现阶段**：可记录实现决策，不对比原代码
3. **验证阶段**：只记录测试结果，不分析代码差异
```

## 5. 风险与应对

### 风险 1: AI 隐性记忆

AI 模型的训练数据可能包含类似代码。

**应对**：
- 无法完全消除（模型固有特性）
- 规格尽量抽象，减少与训练数据的关联
- 法律上仍需律师确认

### 风险 2: 规格遗漏关键功能

新实现可能缺少原代码的功能。

**应对**：
- 规格阶段详细审查
- 测试阶段用原代码的真实用例验证
- 发现遗漏时，回到规格阶段补充（不直接看代码）

### 风险 3: MemPalace 污染

Session A 的代码细节可能被记录到 MemPalace。

**应对**：
- Session A 结束前，审查 MemPalace 记录
- 使用 `mempalace_kg_invalidate` 清除代码细节记录

```
              ↓ 新 Session

┌─────────────────────────────────────┐
│  Session B: 新语言实现                │
│  ─────────────────────────────────  │
│  读取：/raw/specs/*.md               │
│  限制：不打开原代码文件               │
│  输出：新语言代码                     │
│  记录：实现决策（不对比原代码）        │
└─────────────────────────────────────┘
              ↓ 新 Session
┌─────────────────────────────────────┐
│  Session C: 测试验证                  │

```
